# 説明の表示の順の変更と対面の評価に向けた改善

## 1. 概要

BoketeImageAnnotator の説明の軸ごとの頁を，実例のカルーセルを先に示し，軸の説明の文と「次へ」のボタンを1つの吹き出しにまとめる順に変えた．また，早見表（report_037）を示しながら LINE で回答してもらう対面の評価を翌日に行う前提で，運用上の問題点を検討し，表示の版の確認，デバッグモードの検出，実施中の進み具合の表示，当日の手順の文書化を行った．表示が変わったため表示の版を5とし，早見表を版5で作り直した．

| 項目 | 内容 |
| :--- | :--- |
| 変更 | `src/messages.ts`（`tutorialMessages`），`src/content.ts`（判定の方法で早見表に触れる），`src/labels.ts`（`UI_VERSION = 5`），`scripts/serve_image_quick_tunnel.mjs`，`scripts/stats_image_local.mjs`（新規．`npm run image:stats`），README.md |
| 確認 | vitest 14件，型の検査，模擬試験（全項目合格．回答の表示の版が5），`image:stats` の模擬試験の D1 と運用の D1 での実行，早見表の作り直し（版5） |
| コミット | `ada6224` |

## 2. 説明の表示の順

従来は軸ごとに「軸の説明の文（テキストのメッセージ）」「実例のカルーセル」「確認できたら次へ（ボタンの吹き出し）」の3件を送っていた．変更後は「実例のカルーセル」「軸の説明の文と『次へ』のボタンを持つ吹き出し」の2件とした．吹き出しの表題は「【説明 1/4】形式」のように頁の番号と軸の名前を示し，本文の末尾に「上の実例は左右にスクロールすると全て見られます．」を添えた．LINE のトークの画面では最後のメッセージが最も下に表示されるため，評価者は実例を見た後に説明の文を読み，そのまま「次へ」を押せる．評価の途中の「説明」のコマンドも同じ表示となる．

## 3. 対面の評価に向けた問題点と対策

| 問題点 | 対策 |
| :--- | :--- |
| 早見表と Bot の文言の版がずれると，紙と画面の定義が食い違う | 起動時に「表示の版：5」を表示し，早見表の右上の版と照合できるようにした．早見表は同じ `labels.ts` から作るため，作り直せば一致する． |
| デバッグモードのまま起動すると，ブロックの解除で参加者の回答が削除される | `--debug` のときの注意に加え，`.dev.vars` に `DEBUG` がオンで書かれている場合も起動時に警告する（値は表示しない）． |
| 開発者の試しの回答が本番の回答に混ざる | 対面の評価の回答は表示の版5となり，版4以前の試行と区別できる．当日の動作確認の回答は「参加をやめる」で削除する手順とした． |
| 実施中に参加者が進んでいるか，止まっているかが分からない | `npm run image:stats`（`--since HH:MM` で開始の時刻以降に絞る）で，状態ごとの人数，表示の版ごとの回答数，評価者ごとの回答数・注意確認の不合格・平均の回答時間・最後の回答の時刻を匿名の番号で表示する．ローカルの D1 を読むのみで，動作中の Bot に影響しない． |
| 実施中に起動し直すとクイックトンネルの URL が変わり，送った吹き出しの画像が表示されなくなる | 当日の手順に，実施中は起動し直さないこと，PC のスリープを止めることを明記した． |
| 早見表があることを Bot の説明が前提としていない | 判定の方法の説明に「早見表（紙や画面）が配られている場合は，あわせて参照してください．」を加えた． |

当日の手順は README.md の「対面での評価」にまとめた．前日の試験と早見表の作り直し，開始前の起動（`--debug` なし）と版の照合，自分のスマートフォンでの動作確認と試しの回答の削除，実施中の `image:stats` での確認，終了後の `export_results.py --ui-version 5` での集計からなる．

運用のローカルの D1 で `image:stats` を実行したところ，ブロック中でない評価者は1人（評価中）で，表示の版4の回答が25件あった．これは動作確認の回答とみられ，版5の回答とは区別される．

## 4. 未解決の論点と次の作業の候補

- 動作中の `npm run image:tunnel` を再起動するまで，新しい説明の順と表示の版5は反映されない．再起動後に実際の LINE の画面で説明の頁の見え方を確かめる必要がある．
- クイックトンネルは稼働を保証しない．多数の参加者が同時に回答する場合の応答の遅れや，会場のネットワークで UDP が通らない場合（`--protocol http2`）は事前に確かめられていない．
- 問題は回答数の少ない順に出題するため，対面の評価では参加者ごとに異なる問題に回答し，同じ問題への複数の回答はほとんど集まらない．評価者の個人差（report_032 の $` s `$）を推定するには，一部の問題を全員に出題する仕組みが必要である．
- 説明の実例の画像には他の軸の要素（写真とイラストの実例のカルタ記号など）を含むものがあり，早見表と説明のカルーセルの双方で紛らわしい可能性がある．差し替えには `examples_override.json` と D1 の examples 表の更新が必要である．
- 回答の版4の25件（動作確認）は，本番の集計では `--ui-version 5` で除く．
